A spatial job deserves its own compute.

A map request and a two-hour analysis should be able to scale independently. Here’s how Honua separates serving, job coordination, and processing.

When a script becomes a shared job.

A script starts on one person’s laptop. Then a colleague needs to run it, check its status, retrieve the result, or use a larger dataset. It now needs to work as a shared job.

An HTTP endpoint is only part of that. The job needs an identity, state that survives the serving process, a worker that can run it, and results someone else can inspect.

Consider a recurring exposure analysis: select assets, run the supported spatial operations, keep the parameters, and make the outputs available. This is an example to evaluate with your chosen process and backend. It does not mean any Python script can be submitted unchanged.

From submission to result.

Submit→Validate→Coordinate→Execute→Inspect results

The serving layer accepts the request and tracks the job. Shared coordination stores its state independently of that serving process. A supported worker or batch backend runs the work.

GPServer, OGC API Processes, gRPC, and MCP connect to a shared asynchronous job runtime. The documented durable-job path requires Redis, so the job’s lifecycle does not depend on keeping one HTTP process alive.

Validate the plan and inputs before execution. Supported interfaces let clients check progress and status, cancel work, and retrieve results. An accepted request means the system took the job; the client still needs to check whether it finished successfully.

Scale map requests and processing separately.

The serving tier handles interactive traffic. Heavy processing runs with resources sized for its process and dataset. Native dependencies live with the worker that needs them, rather than making every serving instance carry the processing environment.

You can start with containers and move to Kubernetes or cloud container services. Suitable processes can run as Kubernetes Jobs or on supported cloud batch backends. The backend must support the process, with the right credentials and dependencies in place.

Autoscaling can still be expensive. Account for minimum capacity, the database, coordination, startup delays, data transfer, and utilization. Compare the total cost while meeting the latency and reliability your workload needs.

Retries, cancellation, and incomplete results.

Check what a retry does to the output. It should not silently create duplicates, and a failed or cancelled run should not look complete. Storing job state makes failures inspectable; it does not by itself make rerunning an operation safe.

Interrupt a worker or disconnect the client during an evaluation. Check which state survives, whether the job can recover or be safely resubmitted, and how the system reports partial outputs. Do this on the backend you plan to use.

Working with Python.

The Python SDK covers feature access, administration, and geoprocessing alongside the wider Python ecosystem. ArcPy-oriented migration tools classify and convert supported code patterns and leave unsupported behavior for review.

Check the documentation for the package you install; the development branch may describe newer capabilities. Begin with a repeatable process whose inputs and expected result you know.

Test a representative job.

Choose a process your team actually runs. Record its data, parameters, runtime version, resource limits, and backend. Measure queue and execution time, check the output, test failures, and account for the full infrastructure cost.

Then run interactive queries at the same time. Check whether they remain responsive while the processing workload gets the resources it needs.

The aim is a job your colleagues can run again, check, and troubleshoot without depending on the laptop where it started.
