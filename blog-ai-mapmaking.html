Inside real-time AI mapmaking.

Describe a map, refine it in conversation, and save the result. Here’s how Studio turns those requests into changes.

Honua · Engineering notes · Technical scope reviewed 2026-10-14

Preview Studio is a self-hosted Preview with support for vector sources. This article explains the implementation; a hosted demo is not available.

Start with a map request.

Take a request such as “Show the inspection locations, color them by status, and add a table.” This example illustrates the workflow: the model chooses tools, Studio applies the changes, and you see the map take shape.

Studio builds geospatial applications with layers, styles, views, tables, charts, and analysis. You choose the model it uses.

It starts with the live catalog and the data your identity is allowed to access. The model cannot grant itself access, invent a catalog layer, or change source records.

How a request changes the map.

The SDK’s StudioAgentSession tells the model which tools are available, executes the calls it selects, and sends the results back. The map can update while those calls stream.

Intent→Model + tools→Typed command→Map state

We use a defined set of commands rather than executing arbitrary JavaScript from the model. The composition reducer or the server’s Studio MCP tools apply each change.

Each command identifies the change and its parameters, and an activity log records the actions. You can inspect what happened. These controls don’t guarantee a useful map: the model can still choose the wrong field or produce poor styling.

Change the map, keep the source data.

You might then ask for a different color scheme or a narrower view. Studio changes the application’s composition and leaves the source dataset alone.

Agents cannot directly edit source feature data. Editing a draft also does not grant permission to publish it; publication is a separate action.

The current renderer supports vector sources through OGC API Features or GeoServices FeatureServer. It does not yet render raster, image, or 3D layers. Unsupported layers are shown with an explanation.

Save, reopen, and publish.

Studio saves compositions using the SDK’s package format and the server’s package lifecycle. You can keep drafts, create immutable versions, compare them, publish, and roll back. The saved application lives on the server, beyond the browser session.

Governed sharing remains Preview and requires approval through the supported workflow. Version history covers the composition; it does not make every external side effect reversible.

Use your chosen model.

The server’s Studio AI proxy connects to your chosen hosted or local model. Provider keys stay out of the browser.

Models differ in how well they choose tools and build maps. We test repeatable fixture conversations separately from real-model conversations. Passing a scripted test does not tell you how a model will handle every request.

Try it with your own layer.

Run the self-hosted Preview from source. The README explains how to use a real model or deterministic fixture conversations, and which checks are required for a release.

Studio’s GP panel currently uses a test job store. It does not yet demonstrate live execution through the batch backend. Server-side geoprocessing can be evaluated separately.

Start with a supported vector layer and a specific task. Check the selected data, fields, and styling, then save and reopen the application. Test permissions and publication as well. Try further requests with your chosen model, and review the spatial details: coordinate systems, data quality, and interpretation still need your judgment.
