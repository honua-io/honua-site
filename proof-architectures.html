Reference architectures

← Back to proof & claims

These reference architectures let an evaluator map Honua onto an environment without mistaking a design for a certified deployment. Each shape is labeled as source-backed, preview, private beta, or roadmap.

The building blocks are grounded in source: Honua Server runs on .NET 10 (the runtime used by the GeoBench harness), is packaged as a container image, has a public Helm chart, stores features in PostGIS / PostgreSQL, supports object-storage paths for bounded artifacts, and emits OpenTelemetry. Terraform, HA, and GitOps paths are at the evidence levels shown below; they are not all production-certified.

Cross-cutting principles

  • Standards + Esri on one server. A single Honua deployment exposes documented GeoServices REST and OGC API Features / WMS / WFS / WMTS / WCS / STAC surfaces. Coverage varies by operation; see the Compatibility Matrix.
  • Stateless server tier, stateful data tier. Scale the Honua server tier horizontally; keep state in PostGIS and object storage.
  • Observability by default. OpenTelemetry traces/metrics from the server tier into the operator's existing backend.
  • Security posture: TLS termination guidance, OAuth2 / API-key / token auth, policy-scoped authorization, structured security events, and DPA terms for commercial engagements are documented. Durable audit storage and compliance dashboards are not baseline server features. SOC 2 Type II is on the roadmap; see the security status table.

B. Cloud-native HA on Kubernetes / AKS — Preview

The public Helm chart describes a horizontally scaled server tier behind an ingress with managed PostgreSQL/PostGIS, shared object storage, and Redis. Treat this as an evaluation and pre-production path until immutable releases and live upgrade/rollback evidence are published.

  • Use for: evaluation and pre-production HA testing on AKS or Kubernetes; production certification remains roadmap work.
  • Evidence: the public honua-helm chart and private honua-iac modules under active hardening. Multi-node mode requires shared storage and Redis; unsafe defaults are being closed before a stable module release.

C. GitOps-managed operations — Private beta

The source-backed GitOps engine can plan, diff, sync, and roll back one environment. The guarded operator loop and rollback release gate are implemented, but exact release-candidate binding, post-action convergence, and coordinated fleet promotion are still being completed. This is private beta, not an unqualified production claim.

  • Use for: auditable, repeatable, reversible deployments of a single environment from git — plan, review, apply, roll back. (Coordinated promotion across a dev → staging → prod fleet is on the roadmap, capability-gated, not yet shipped.)
