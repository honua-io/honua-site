sdk-js is behind a known-bad window — upgrade to the policy-approved target

KB-COMPAT-0001 · policy window HONUA-COMPAT-JS-001 · applies to @honua/sdk-js

← Client & SDK version compatibility matrix

This is the reference pattern for the compatibility KB: a resolved guided-fix promoted to a published article. The same shape applies to every known-bad window in the compatibility policy — the identifiers differ, the resolution shape does not.

Symptom

Requests from Honua sdk-js 5.x against a server on the 2.4+ family fail — typically FeatureServer query calls returning HTTP 400 / rejected-parameter errors that did not occur against older servers.

Diagnosis

This pairing is a documented known-bad window in the versioned compatibility policy, not a bug in your query:

Policy windowHONUA-COMPAT-JS-001
SDK range>=5.0.0 <6.0.0
Server range>=2.4.0 <3.0.0
Whysdk-js 5.x emits legacy FeatureServer query parameters that server 2.4+ rejects; the pairing is a known-incompatible window.

Confirm your versions. The SDK version is in your lockfile / package.json; the server version is on the server's info endpoint.

npm ls @honua/sdk-js          # your sdk-js version
curl -s https://YOUR-SERVER/rest/info | jq .currentVersion   # server version

If sdk-js is in >=5.0.0 <6.0.0 and the server is in >=2.4.0 <3.0.0, you are in the known-bad window.

Resolution — upgrade to the policy-approved target

Move sdk-js to the policy-approved upgrade target: 6.2.0. That is the highest sdk-js version support has cleared against the deployed server 2.x family. It lands inside the supported window >=6.0.0 <7.0.0, which is verified against server >=2.4.0 <3.0.0.

npm install @honua/sdk-js@6.2.0

Do not jump to the newest release. sdk-js 7.x is a major that is not approved against server 2.x. The approved target is deliberately not "latest" — it is the highest version cleared against the server family you are actually running. Upgrading the server past 3.0.0 is a separate change with its own approved client target.

Verify

After upgrading, re-run the failing FeatureServer query. It should now succeed, and the (sdk-js 6.2.0, server 2.4+) pair resolves to supported on the compatibility matrix.

The same pattern for the other SDKs

Every first-party SDK has an equivalent known-bad window and approved target. Match your symptom to the right window on the compatibility matrix and upgrade to that row's approved target:

KBSDKKnown-bad windowUpgrade to

KB-COMPAT-0002Honua.Sdk (sdk-dotnet)>=3.0.0 <4.0.0 (HONUA-COMPAT-DOTNET-001)4.3.0
KB-COMPAT-0003honua-sdk (sdk-python)>=1.0.0 <2.0.0 (HONUA-COMPAT-PYTHON-001)2.5.0

These values are the same ones that drive the generated matrix — canonical source: compatibility-policy.v1.json in honua-io/honua-support (honua-support#42). When a full article is promoted for KB-COMPAT-0002 / KB-COMPAT-0003, it follows this same symptom → diagnosis → approved-target shape.

Still stuck?

If your versions are inside a supported window but you still see failures, it is not this known-bad window — get in touch with your sdk-js version, server version, and the failing request.
