A certified AWS stack on the infrastructure you already trust.

Honua fits into a normal cloud platform architecture, so GIS does not need its own isolated operating model.

01 · Certified GA: AWS Launch Stack

One CloudFormation stack on ECS Fargate (x86_64).

Launch Honua directly into your AWS account with CloudFront, AWS WAF, a private VPC origin to an internal ALB, digest-pinned ECS Fargate (x86_64) tasks, S3/CloudFront Console, and an independent watchdog — with no Terraform or separate build pipeline required. Public honua-iac Terraform modules remain available for teams standardizing on Terraform.

02 · Data stays yours

Keep PostGIS as the operational system of record.

Connect the database you already secure, back up, and monitor. Store bounded artifacts in S3 or MinIO, keep durable job queues and workflow state in PostgreSQL with zero Redis, and serve supported COG, PMTiles, and GeoParquet workflows without first moving every object into a proprietary store.

03 · Signals travel

Bring GIS into your existing observability practice.

Health and readiness endpoints work with platform probes and the Launch Stack watchdog. OpenTelemetry exports traces, metrics, and structured logs to the backend you configure, giving GIS requests the same operational context as other services.

Add capacity where the workload needs it.

Start with one Fargate task, then autoscale serving replicas as traffic grows. Multi-node deployments share PostGIS and object storage; durable jobs, imports and workflow state live in PostgreSQL, so there is no separate coordination service to run. Put finite tile and artifact keys behind your CDN, and size PostGIS independently for the data and query load.

Certified GA · AWS ECS Fargate

Launch Stack or Terraform on x86_64.

The native AWS CloudFormation Launch Stack provisions CloudFront + WAF, private VPC origin, internal ALB, ECS Fargate (x86_64), RDS PostGIS, S3/CloudFront Console, and automated backups. Teams running Terraform can deploy the same ECS Fargate architecture with weighted ALB target groups through honua-iac aws-ecs.

Preview · Kubernetes & Lambda

Fits existing cluster or serverless estates.

The public Helm chart deploys the same OCI web image to Amazon EKS or conformant Kubernetes clusters, and honua-iac aws-serverless targets AWS Lambda with the *-lambda-aot image. Both remain Preview in 2026.1.

Batch compute

Geoprocessing runs off the request path.

Long-running geoprocessing and import jobs dispatch to a remote batch backend instead of the serving container. The Launch Stack includes optional AWS Batch on Fargate with zero idle charge, and Kubernetes deployments can use Kubernetes Jobs.

  • AWS Batch
  • Kubernetes Jobs

Runtime requirements and a measured datapoint.

Honua does not publish a requests-per-pod sizing rule. Two public numbers exist: one measured datapoint with a disclosed profile, which is a dated snapshot that cannot be reproduced exactly (the benchmark page states its own limits), and the prospective 2026.2 billing ceiling for a serving unit. 2026.1 licensing is disabled; serving-unit bands are neither measured nor enforced. Use them as rough anchors, then validate against your own workload.

Measured datapoint · GeoBench, April 28, 2026

A 4-CPU-core / 4 GB container sustained the published per-scenario figures.

In the historical GeoBench snapshot, the Honua server container was limited to 4 CPU cores and 4 GB memory (PostGIS and the k6 load generator each ran in their own 4-core / 4 GB container), with no spatial response cache and disclosed bounded active-query/pool settings 6/6/3, against a 100K-point dataset. Within that profile it sustained 1632.8 req/s at p95 5.2 ms on the attribute-filter LIKE scenario, 937.2 req/s at p95 13.8 ms on GeoServices FeatureServer/query (medium bbox), and 1190.2 req/s at p99 201.4 ms under the 100-VU concurrent mixed workload.

A datapoint, not a guarantee

Validate sizing against your workload during a pilot.

The figures above come from one disclosed profile and are not a sizing guarantee. Your data model, query mix, cache policy, and latency targets will move them. The GeoBench harness ↗ is Apache-2.0: point it at your own dataset and query mix as a sizing tool, then confirm the result during a pilot.
