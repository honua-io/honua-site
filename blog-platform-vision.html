More time for spatial work.

We want analysts to spend more time answering questions and less time setting up the work. GIS administrators should be able to use the same deployment and monitoring tools as the rest of their organization. Developers should be able to put spatial data into the applications people already use.

That’s why we’re building Honua as a spatial platform. The server is part of it, alongside applications, analysis, automation, and the tools to run them.

Automate migration. Create with AI. Scale with demand. Operate with confidence.

Bring what you have.

Honua does many of the same jobs as ArcGIS Server, GeoServer, and other GIS tools. That overlap is intentional. Teams need familiar capabilities and interfaces when they move to another platform.

Moving a service, importing its layers, and adapting an application are different tasks. Honua has automated imports and code-conversion tools for supported workflows. Start with an inventory, check compatibility, review the output, and test the workflows before switching over. You can migrate one workflow at a time. Some code and service behavior will still need manual work.

Build what comes next.

We use AI extensively to build Honua. We’re also designing it so people can use agents to do spatial work and help operate the platform.

In Studio, an agent uses typed commands to select layers, change styling, and adjust views. You can save the resulting map or application, reopen it, and compare versions.

Studio is currently a self-hosted Preview. Agents use the platform’s supported interfaces and permissions. They cannot directly edit source feature data.

Scale the work—not idle infrastructure.

A map request and a two-hour spatial job should be able to scale independently. Honua separates request serving, durable job coordination, and processing so they can each have the resources they need.

That gives teams a choice of containers, serverless runtimes, scalable clusters, and batch backends. The aim is to reduce the idle capacity of an all-purpose server sized for peak demand. Whether it saves money depends on the workload and deployment; measure the full infrastructure cost.

Data movement matters too. Our open geospatial gRPC protocol provides typed requests and streaming results alongside the GIS standards and APIs the platform supports.

Make change routine—and reversible.

Upgrades should be normal maintenance. Git-backed configuration lets you review a change, versioned artifacts identify what you deploy, and telemetry helps you check the result. Supported operations include checks before and after the change, with recovery when needed.

The Ops Inbox shows what needs attention, the evidence behind it, and a suggested fix when one is available. Permissions and approval policies control what can run, and recovery needs to be verified. A container starting successfully tells you very little about whether someone can still use the service. Check their workflow too.

Make adoption understandable.

Our feature registry records which capabilities belong to Community, Pro, and Enterprise. Separately, commercial pricing will scale with usage or deployed capacity, without a Honua named-user fee. We’re still working out the units, bands, and rates.

Honua Server and Collect use ELv2. Other platform components use Apache 2.0. The mobile SDK and Collect app are experimental. Licenses, editions, release maturity, and support are separate questions.

The components are at different stages. Use the capability catalog and the documentation for your release to see what is available, what is experimental, and what has been tested.
