Install Honua
with your agent.

Two paths, one agent. Evaluate a digest-pinned preview on your own machine, or deploy the qualified ECS/Fargate stack into your AWS account through the honua-devops operator. Either way the agent follows the published guide, shows you what it will do, and asks before it does it.

AWS, through the operator.

Install the honua-deploy-aws skill, then ask your agent to deploy Honua on AWS. The skill teaches Claude Code or Codex to use the honua-devops MCP operator, starting with install_honua. The operator owns planning, signed-approval checks, apply and verified handoff; the skill does not run Terraform itself.

Use v2026.1.3. Its archive includes skills/honua-deploy-aws/SKILL.md. v2026.1.2 predates the skill; for that older archive, use the paste-prompt fallback below with the manual MCP quickstart. Use the skill and binary from the same archive.

Install once, then ask.

Download the self-contained archive for your machine, verify its digest, and copy the included skill into your project’s .claude/skills/ directory for Claude Code or .agents/skills/ for Codex. Register the matching executable as an MCP server. In MCP mode your client's model does the reasoning, so the operator needs no model provider key.

In Claude Code, ask: “Use /honua-deploy-aws to install Honua on AWS. Show me the exact plan before I approve it.” In Codex, ask: “Use $honua-deploy-aws to install Honua on AWS. Show me the exact plan before I approve it.”

The path stays on the honua-iac v0.6.1 ECS/Fargate small preset in an allowed non-production environment. It requires pre-existing locked remote state, an administrator-exported deploy-identity contract and a matching short-lived assumed-role session. The agent must stop for missing administrator setup, show the account, region, resources, cost drivers and plan digest, and obtain a separately signed approval for that exact plan. No IAM users or long-lived keys are created; only the verified install handoff counts as readiness.

Prefer to run Terraform yourself?

Operator deployment guideDeploy on AWS and Azure

The honua-devops operator and the honua-iac modules are Fair Source (FCL-1.0-ALv2), like Server and Collect: run them to operate your own Honua estate; competing use needs a separate agreement. honua-iac also ships a qualified AWS Lambda stack and Azure previews; the agent path stays on ECS/Fargate until their first-install workflows are qualified. How the operator is scored: multi-model operator evals.

1 · Download and verify the matching archive
VERSION=v2026.1.3
ASSET=honua-devops-linux-x64.tar.gz   # macOS: osx-arm64 or osx-x64

gh release download "$VERSION" --repo honua-io/honua-devops \
  --pattern "$ASSET" --pattern "$ASSET.sha256"
sha256sum -c "$ASSET.sha256" || exit 1   # macOS: shasum -a 256 -c

INSTALL_DIR="$HOME/.local/share/honua-devops/$VERSION"
mkdir -p "$INSTALL_DIR"
tar -xzf "$ASSET" -C "$INSTALL_DIR" || exit 1
test -f "$INSTALL_DIR/skills/honua-deploy-aws/SKILL.md" || exit 1

On Windows, use honua-devops-win-x64.zip, verify its SHA-256 with PowerShell Get-FileHash against the adjacent checksum before Expand-Archive, and register the absolute path to Honua.DevOps.Agent.exe.

2 · Install the skill and register your client
# Claude Code (choose this or the Codex alternative below)
mkdir -p .claude/skills
cp -R "$INSTALL_DIR/skills/honua-deploy-aws" .claude/skills/
claude mcp add honua-devops -- "$INSTALL_DIR/Honua.DevOps.Agent" --mcp
claude mcp list

# Codex alternative
mkdir -p .agents/skills
cp -R "$INSTALL_DIR/skills/honua-deploy-aws" .agents/skills/
codex mcp add honua-devops -- "$INSTALL_DIR/Honua.DevOps.Agent" --mcp
codex mcp list

Restart your agent session if needed and confirm install_honua is available. Then use the skill request shown alongside. Codex registration syntax: official MCP documentation.

Fallback · Paste into your MCP client
Deploy Honua into my AWS account with the honua-devops operator and the honua-iac Terraform stacks.

Start with the honua-devops install_honua tool registered in this session. It runs the whole install in order: intake, topology recommendation, one saved plan, my approval, apply, and the verified install handoff, using describe_environment, recommend_deployment_topology, provision_infrastructure, install_handoff and verify_install_handoff. Use honua-devops v2026.1.3. If these tools are not registered, stop and walk me through the registration steps in https://github.com/honua-io/honua-devops/blob/trunk/docs/QUICKSTART-MCP.md. Do not improvise a different install path.

Read the operator deployment guide before planning: https://github.com/honua-io/honua-iac/blob/trunk/docs/operator-deployment.md. Use honua-iac v0.6.1, the release whose least-privilege deploy identity the operator requires. Target AWS ECS/Fargate (the aws stack), the 2026.1 ECS target, at the small preset. If I request another target or size, stop and explain this entry point's limit. Do not choose Azure, EKS, Helm or a mixed topology.

Before anything touches my account: tell me which AWS account and region my credentials resolve to, confirm Terraform >= 1.5 and < 2.0 (>= 1.10 for S3 state locking), and verify the pre-existing locked remote state, administrator-exported deploy-identity contract and matching short-lived assumed-role session. The operator refuses local state and unqualified apply. Stop for missing administrator setup; do not create state buckets, OIDC roles or execution-identity roles, or run Terraform directly. Use dev, staging or it only when also allowed by the operator host.

Produce the Terraform plan and show me the resources it will create, the cost drivers that keep billing afterwards (RDS PostGIS, Fargate tasks, load balancer, NAT, storage), and the plan's approval digest. Apply nothing until I approve that exact plan and a separate approver supplies the signed receipt for it; never regenerate a different plan after approval. Use an independent KMS signing principal for governed approval, with only VerifyMac permission for the operator principal. Never create IAM users or long-lived access keys. Never print secrets, passwords, state files or credentials into the chat.

Retain the installationId and follow install_honua through handoff and verification using the same host-authorized execution settings. After apply: capture honua_url and the database endpoint, run the guide's health checks, write the install handoff and verify it. Provisioning success alone does not mean the server is ready; only the verified handoff does. Then show me how to point my MCP client at the installed server's /mcp endpoint for day-2 operations.

If anything fails, diagnose it and report the actual error. Do not retry destructive operations, delete state, or tear down resources without asking me first.

Finish with: target, account and region; the honua-iac and honua-devops versions used; the plan digest and apply receipt; endpoints; the checks performed; and the documented teardown command.
