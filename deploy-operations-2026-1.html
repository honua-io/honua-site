Honua 2026.1 supported operating envelope

Source of truth: honua-release. Evidence snapshot: 2026-09-05 UTC (2026-09-04 HST). Release decision: HOLD; the candidate is not yet cut. This document records qualification boundaries, not permission to promote.

The quality contract and amendments define the GA scope. The September 4 cloud-native, whole-catalog GP and release-integrity rulings apply. A scope decision is not an execution receipt. The release decision record separates implementation from qualification. Throughout this page, not qualified in 2026.1 means that the cited evidence does not establish a supported operating claim; it never means unlimited capacity.

1. Deployment topology and component versions

The release lock draft is explicitly incomplete and unqualified. No complete exact-candidate deployment/component set is qualified in 2026.1 at this snapshot. Use the eventual signed release lock and its exact artifact-pair receipts when choosing production versions; a compatible version range or a published package alone does not establish a qualified pairing.

3. What happens when a limit is reached

Configured controls and receipt-backed qualification are different facts. There is no candidate-bound, topology-specific overload/recovery receipt here, so graceful behavior at the complete operating envelope is not qualified in 2026.1. Use the protocol error returned by the supported SDK/CLI/MCP path; do not assume every rejection is an HTTP rate-limit response or that a timeout proves a mutation did not run.

Limit or failure boundary Current behavior and customer consequence
Request body with declared length above the configured cap The pinned limits middleware rejects before the handler with status 413, message Request payload exceeds maximum allowed size, and the configured maximum in the detail. Its protocol formatter selects the route's error envelope. This is a source-confirmed error contract, not a topology qualification receipt; tested payload ceiling: not qualified in 2026.1.
Cooperative handler observes the request deadline before response starts The same middleware emits status 408, Request timeout, with the configured duration in the detail. It cannot replace a response already started, and handlers must observe its deadline token. This conditional rejection contract is source-confirmed; complete topology/deadline qualification is not qualified in 2026.1. Maps is a known exception below.

Respect that delay through the supported client. This describes the rejection branch, not proof that admission is atomic or all GP transports share the same status; throughput/concurrency qualification: not qualified in 2026.1.

Broken promise: the supported backup/recovery workflow must account for enabled job/workflow state. See the procedure caveat below.

The admission rule requires every newly discovered blocker to name a broken security/isolation, data-integrity or documented supported-workflow promise. A missing measurement alone is recorded as unqualified, not as evidence of a product defect.

4. Backup procedure and recovery expectation

Follow the pinned backup and restore runbook for database and file handling, with the durable-substrate caveat below:

  1. Inventory the deployment's durable state: PostgreSQL data/metadata, migration journal and transactional outbox; configured upload/attachment/output stores; Redis job queue, logs and workflow state where enabled. Record the exact image, configuration, backup identities and checksums. Keep secrets outside this record.
  2. Use PostgreSQL pg_dump in custom format, with tools matching the database major version. Coordinate file-volume snapshots or bucket versioning/replication with the database backup so referenced bytes and metadata match. Verify that archives are readable and expected files are present. Database WAL/PITR is an infrastructure-owned option, not evidence of a tested Honua recovery objective.
  3. Stop traffic and writers before restore. Use pg_restore into a clean database and restore matching file/object state before starting the application. Ensure required extensions exist and select an image compatible with the restored migration journal. Startup may apply forward migrations.
  4. Restart and verify readiness plus an actual supported-client catalog/feature journey. Check restored counts/checksums and referenced output bytes. For enabled workers, Redis and outbox, prove restart recovery through real runtime paths; a catalog browse alone does not establish job recovery or outbox delivery.

Redis caveat: the pinned runbook's store table says to exclude Redis from restore planning, while its durable-job loss contract says Redis holds required job/workflow state. Do not interpret that exclusion as a full-platform backup procedure. AOF/reconnection guidance concerns restart resilience; it does not prove recovery after primary-state destruction. Complete Redis/output/outbox backup and recovery is not qualified in 2026.1, as documented by release#257. The server runbook correction is tracked as server#4352.
