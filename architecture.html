THE OPERATING LOOP

Know what changed.
Know how to recover.

The Ops Inbox connects a finding to its evidence, proposed action, decision, and outcome. AI can help inspect and propose; authority stays with the platform.

  1. 01Observe

    Health, traces, metrics, and the service’s actual operating posture.

  2. 02Diagnose

    A bounded finding with supporting evidence and an available action.

  3. 03Propose

    Review the affected resources, expected result, and recovery path.

  4. 04Approve & apply

    A separate authorized principal approves agent proposals.

  5. 05Verify & recover

    Check the supported workflow; restore the previous version when protection requires it.

A durable history, not a blind undo.

Git-backed definitions make configuration changes reviewable. Immutable releases identify deployed code. Durable operations record execution and results. Configuration revert, application rollback, and database restoration remain distinct.

Automation within explicit limits.

Selected low-risk remediations can follow opt-in policy, guardrails, audit, and a kill switch. Proposal-only is the default. Unsupported actions stop before mutation; unproven recovery requires attention.

Safety belongs in the workflow.

Direct editing of source feature data is not exposed to AI agents. Protected updates depend on supported executors, trustworthy telemetry, and a compatible recovery path. No blanket zero-downtime or universal rollback promise.
