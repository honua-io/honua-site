THE OPERATING LOOP

Know what changed.
Know how to recover.

The Ops Inbox shows a problem, its evidence, a proposed action, and the result. AI can help investigate and suggest a fix; the platform’s permissions and approval rules still apply.

  1. 01Observe

    Check service health, traces, metrics, and current configuration.

  2. 02Diagnose

    Identify a specific problem, its evidence, and a supported action when available.

  3. 03Propose

    Review the affected resources, expected result, and recovery path.

  4. 04Approve & apply

    A separate authorized principal approves agent proposals.

  5. 05Verify & recover

    Check the supported workflow; restore the previous version when protection requires it.

Keep the history of each change.

Review configuration changes in Git, identify deployed code by its immutable release, and keep execution records and results. Reverting configuration, rolling back an application, and restoring a database are different procedures.

Choose what can run automatically.

Changes are proposal-only by default. Selected low-risk fixes can run automatically under an opt-in policy, with guardrails, audit, and a kill switch. Unsupported actions stop before making changes. Recovery that cannot be verified requires attention.

Check the recovery path.

AI agents cannot directly edit source feature data. Protected updates require a supported executor, trustworthy telemetry, and a compatible recovery path. Not every change can be rolled back or completed without downtime.
