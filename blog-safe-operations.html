Plan the recovery before the rollout.

A GIS upgrade should have a recovery plan before it has a deployment date. Small, repeatable changes make upgrades easier to do regularly. They still need checks before and after rollout.

Operators and agents can inspect the same health information, findings, proposals, and execution records through Console and the platform interfaces. The server holds the authoritative operational state.

The Ops Inbox starts with a finding.

An alert is more useful when you can see what triggered it and what to do next. In the Ops Inbox, a finding describes a specific condition, links to the evidence, and identifies an available action when there is one.

The documented finding checks run on demand and use deterministic rules. They do not need a server-side model call. An agent can inspect the health information and evidence, explain the problem, and propose a supported action.

A finding does not always have an automatic fix. High latency, for example, can have several causes. The system may be able to identify or explain a problem without having a safe action to apply.

Who can approve a change?

Finding→Proposal→Approval→Operation→Evidence

A separate authorized identity approves agent proposals through the platform’s operation controls. The agent cannot approve its own work or create another approval path.

By default, the system proposes changes rather than applying them. You can opt selected deterministic, low-risk actions into automatic execution. Each needs a supported executor, explicit policy, guardrails, limited impact, durable coordination, an audit record, and a kill switch.

Agents cannot directly edit source GIS data. The running system’s supported-operation catalog determines which actions can execute.

What happens during a protected update.

Before a protected operation activates a change, it checks the plan and whether recovery is available. It monitors the result for a defined protection window. It then confirms success or, when policy requires, restores the previous version and verifies the recovery.

Missing or untrusted telemetry can block a new change. An operation that was already approved may have a policy requiring deterministic recovery when telemetry disappears. That policy covers recovery of this operation, not permission to make another change.

After switching traffic or receiving a provider acknowledgement, check the affected workflow. Those signals alone do not prove recovery. An operation stays in need of attention when the system cannot verify that the workflow works again.

Revert, rollback, and restore.

Configuration revert changes the desired definitions and records the change in Git. Release rollback switches the deployed application artifact. Data restoration recovers database or artifact state through a separate procedure.

Choose the procedure for the failure you have. A Git revert will not recover overwritten feature data, and an older container may not work with a newer database schema. The recovery path has to account for those compatibility limits.

Keep the history of what was approved, what ran, which version was active, and what happened afterward. That record helps you choose and explain a recovery; it cannot undo every kind of change.

Check the workflow that failed.

Before closing the operation, check the workflow that prompted it. Record the result alongside the change and its supporting evidence.

For a software defect, that means connecting the support case to a reproduction, a regression test, a reviewed fix, and a qualified release. Install the fix and repeat the original workflow. We’re building toward an automated support journey; that complete chain is not automated today.

The goal is to make it easier to keep improving the platform because you know what changed, how it was checked, and how to recover.
